# Contributing

Use GitHub issues for reproducible bugs and feature proposals. For a substantial
change, discuss the scope in an issue before implementing it. Use the private
reporting route in [SECURITY.md](SECURITY.md) for vulnerabilities.

## Development

Install Go 1.27.2, clone this repository and work on a branch. All required
dependency sources are included; no private repository access is needed.

```sh
go test -mod=vendor -race ./...
go vet -mod=vendor ./...
```

Keep changes focused, add a regression test for a behavior change, and describe
what you tested. Code and public documentation use English. Avoid real hostnames,
customer data and credentials in fixtures. Preserve license and attribution
notices. Contributions to Sentinel are accepted under Apache-2.0; changes to
MIT-licensed dependencies retain their license.

## How pull requests are integrated

GitHub is the public review and issue tracker. Maintainers develop in a separate
repository and publish reviewed source snapshots here, with public history kept
from the first publication onward. We import an accepted pull request into that
development repository, run integration tests, then include it in a public
update. A pull request may be closed with a link to the integrating public commit
rather than merged with GitHub's Merge button. Contributor attribution is kept.

The vendored `nocert.io/common` packages are maintained upstream. You can propose
a change to them here; maintainers will apply it upstream and refresh the vendor
snapshot. Do not run `go mod tidy` or `go mod vendor` in this public tree: those
commands need the upstream dependency workspace. Dependency update requests are
reviewed and regenerated by maintainers.

Public CI runs pull requests on hosted, disposable runners without deployment
credentials. A CI pass is not permission to publish a release.
